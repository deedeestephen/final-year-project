# Data Persistence Layer (Layer 5)

Proposal §3.3 specifies four stores. They are implemented as follows (dev versions in `6-infrastructure/docker/docker-compose.yml`).

| Store | Holds | Code |
|---|---|---|
| **PostgreSQL 16** | Users, roles, permissions, tokens, facilities, patients, clinical records, consents, imaging/histopathology *metadata*, AI registry/jobs/explanations, notifications, sync operations, audit log | `3-application-logic/backend/prisma/schema.prisma`, `5-data-persistence/postgresql/migrations/` |
| **MongoDB 7** | AI reports, imaging metadata documents, chatbot conversations, AI inference logs | `3-application-logic/backend/src/persistence/mongo/collections.ts` |
| **Object storage (S3 API, MinIO in dev)** | DICOM (MRI/TRUS/CT), whole-slide images, explanation images | `3-application-logic/backend/src/persistence/storage/` |
| **Vector DB (Qdrant)** | Chatbot knowledge-base embeddings | `3-application-logic/backend/src/persistence/vector/` |

Large files are **never** stored in PostgreSQL: rows keep only a server-generated `storage_key`, SHA-256, size and MIME type.

## Relational model

```
facilities 1─* users *─* roles *─* permissions        users 1─* refresh_tokens / password_reset_tokens / notifications
facilities 1─* patients 1─* clinical_records          patients 1─* consents
patients 1─* imaging_studies                          patients 1─* histopathology_specimens
patients 1─* ai_jobs 1─* explainability_artifacts *─1 ai_models
sync_operations (idempotency_key unique)              audit_logs (append-only, hash-chained)
patients 0..1─1 users   (a patient's own login account)
```

Conventions: UUID primary keys; `created_at`/`updated_at` as `timestamptz(3)`; a `version` column (starting at 1) on records edited offline (patients, clinical records, consents) for conflict detection in Phase 6; `client_uuid` (unique) so a record created offline keeps one identity across retries.

### Rules enforced by the database (migration `…_constraints_and_audit`)
- **Clinical ranges:** PSA and free PSA ≥ 0; free PSA ≤ total PSA; PI-RADS 1–5; prostate volume > 0; Gleason patterns 1–5; ISUP grade group 1–5.
- **Integrity:** lower-case unique emails; date of birth not in the future; SHA-256 format on file checksums; positive file sizes.
- **Consent:** `WITHDRAWN` requires `withdrawn_at`, and `GRANTED` forbids it.
- **Explainability (NFR-09):** each artifact row has either a stored file or an explicit `unavailable_reason`, never neither.
- **Idempotent sync:** `sync_operations.idempotency_key` is unique.

### Audit log (FR-10)
- `audit_logs` is **append-only**: triggers raise on `UPDATE`, `DELETE` and `TRUNCATE`.
- A `BEFORE INSERT` trigger serialises writers with an advisory lock, assigns `seq`, and sets `prev_hash` (the previous row's `row_hash`) and `row_hash = SHA-256(prev_hash | seq | occurred_at | actor | action | entity | outcome | request | ip | details)`. Client-supplied hashes are overwritten.
- `SELECT * FROM audit_logs_verify_chain()` returns the first broken row, or nothing if the chain is intact. The test suite proves that tampering done by disabling the triggers is detected.
- Limitation: a superuser can still disable triggers. Detection (the hash chain) is the control, and the production plan is an application DB role without `ALTER`/`UPDATE`/`DELETE` rights on this table.

### Encryption of identifiers (NFR-01, NFR-10)
Given name, family name, national ID and phone are stored as **AES-256-GCM** ciphertext (`FieldCrypto`, `3-application-logic/backend/src/persistence/crypto/field-crypto.ts`; layout `version|iv|tag|ciphertext`). The national ID is also stored as an **HMAC-SHA-256** (`national_id_hmac`, unique) so a patient can be found by ID without storing it in clear. Keys come from `FIELD_ENCRYPTION_KEY_BASE64` / `FIELD_HMAC_KEY_BASE64` (generated by `6-infrastructure/scripts/gen-keys.mjs`, never committed). Date of birth stays in clear because age drives clinical logic; it is generalised during de-identification (Phase 14/15).

## MongoDB collections
Each has a server-side `$jsonSchema` validator (`validationAction: error`):
- `ai_reports`: `provenance` **must** be `MOCK` or `RESEARCH_MODEL`, a `disclaimer` is required, one report per `jobId`.
- `imaging_metadata`, `chatbot_conversations` (language must be `en`, `bem` or `nya`), `ai_inference_logs`.

## Object storage
Keys are generated server-side (`imaging/2026/09/<uuid>.dcm`) and validated against a strict pattern, so user filenames never become paths and `../`, `\`, absolute paths, upper case and encoded traversal are rejected. Objects are write-once. The local driver adds a second check that the resolved path stays inside the storage root. The S3 driver treats `403` as an error, not as "missing".

## Commands (run in `3-application-logic/backend/`; secrets are read from the repo-root `.env`)
| Task | Command |
|---|---|
| Create `.env` with random secrets | `node ../6-infrastructure/scripts/gen-keys.mjs --init-env` |
| Start services | `docker compose -f ../6-infrastructure/docker/docker-compose.yml --env-file ../.env up -d` |
| Apply migrations | `npm run db:migrate` |
| New migration during development | `npm run db:migrate:dev -- --name <change>` |
| Seed synthetic demo data | `npm run db:seed` (demo password = `SEED_DEMO_PASSWORD` in `.env`) |
| Mongo validators + indexes | `npm run db:mongo:migrate` |
| Integration tests | `npm run test:db` |

Local ports: **Postgres 5433**, **Mongo 27018** (5432 and 27017 are left free for the locally installed PostgreSQL and MongoDB services), Redis 6379, MinIO 9000/9001, Qdrant 6333. To browse the project database with MongoDB Compass, use the `MONGO_URL` in `.env`.

## Test isolation
`npm run test:db` creates a brand-new database per run (`pca_mhealth_<runId>_test`), applies all migrations with `prisma migrate deploy` (proving the schema builds from clean), and removes only that database afterwards (`KEEP_TEST_DB=1` keeps it). The development database is never reset. `prisma migrate reset` is deliberately not used by automation.

## Seed data
`src/persistence/seed.ts` is idempotent and **synthetic only**: 4 demo users (`admin|clinician|pathologist|patient@demo.pca-mhealth.test`, all `must_change_password`), 1 demo facility, 3 demo patients with encrypted names, and 1 clinical record each. Every row has `is_synthetic = true` and says "SYNTHETIC".
