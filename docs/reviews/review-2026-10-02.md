## 3. Security findings

No high or critical finding was found. Controls checked in the code (not only in the docs): EdDSA JWT with pinned
algorithm, issuer, audience and type; account and session re-read on every request; refresh rotation with
reuse detection and a race-safe claim; Argon2id; deny-by-default guard plus permission guard; facility scoping
on every patient, record, imaging, slide, AI job and sync path (others' ids answer 404); sync idempotency keys
bound to the user; magic-byte upload checks, size caps, partial files removed, downloads sent as
`attachment` with `nosniff`; DICOM and image metadata stripped before the AI copy; FHIR export follows Safe
Harbor (year only, 90+ grouped, pseudonyms by HMAC, no free text); SmartCare URL from config only, no
redirects; constant-time service token check in `app/auth.py`; log redaction of headers, cookies, query
strings and identifiers; helmet, CORS allow-list, body limits; push texts carry no clinical values and are
hidden on a locked Android screen; tokens in Keystore/Keychain; the offline database is SQLCipher with a
random per-install key and refuses to open without SQLCipher; local data is wiped at sign-out and when
another user signs in; Android backup is off and cleartext is allowed only in debug builds to local hosts.

### Medium

- **M-1 (fixed, D-3).** Lockout signed people out. See above.
- **M-2 (confirmed by reading, not fixed: needs the owner's decision).** Two ways to link a patient app
  account, with different safeguards. The admin path (`admin.service.ts:331–360`) needs an exact NRC match,
  refuses a record that is already linked, and notifies the patient. The clinician path,
  `PATCH /patients/:id` with `accountUserId` (`patients.service.ts:236–254`, `297–318`), has none of these:
  no NRC match, no notification, and it silently replaces an existing link (it checks only that the
  *account* is not linked elsewhere, not that the *record* is free). Failure scenario: a clinician types or
  is given the wrong account id (a patient can read their own id from their access token's `sub`); that
  app account then sees another man's results, and the real owner loses access without notice.
  `docs/security.md` says linking "needs an exact NRC match". Four DB test files use the clinician path, so
  it looks intended. Suggested fix: refuse when `patient.userId` is set to another account, apply the NRC
  match, and notify, or remove `accountUserId` from `UpdatePatientDto` and link only through the admin page.

### Low

- **L-1 (fixed, D-4).** Malformed cookie gave 500.
- **L-2 (confirmed by reading).** Account enumeration through the lockout. After 5 failures an existing
  account answers 423 `ACCOUNT_LOCKED` (`auth.service.ts:210–213`, without running the password hash); an
  unknown email answers 401 forever. `docs/security.md` says login responses never reveal whether an account
  exists. Both apps show a message for 423, so changing it is a usability trade-off for the owner.
- **L-3.** Anyone can still lock any account for 15 minutes (true of every hard lockout). After D-3 this only
  delays new sign-ins. A per-IP plus per-account delay would avoid it.
- **L-4.** Push devices are removed at app sign-out and with the account, but not when a password is reset
  or an administrator ends sessions. A lost phone cut off by a reset keeps getting pushes. The texts are
  generic and hidden on a locked screen, so the leak is small.
- **L-5.** Admin dashboard "Latest from the phone app" (`DashboardPage.tsx:292–306`) lists patients' emails
  under a subtitle that says "Counts only: no patient names or results". Administrators can see emails on the
  Users page anyway, but the promise and the screen disagree.
- **L-6 (dependency).** `js-yaml` moderate advisory inside `@nestjs/swagger` (dev and runtime docs only; it
  dumps YAML, it does not parse untrusted YAML). Wait for a non-breaking swagger release.

### Not confirmed (worth a look)

- iOS: `flutter_secure_storage` items survive an app uninstall by default, so a reinstall could restore an
  old session. Not checked: no iOS build is possible on this PC.
- When the optional Claude writer is on (ADR-010, off unless `ANTHROPIC_API_KEY` is set), patient questions
  leave the country. `generate.py` scrubs obvious personal details first, but names cannot be scrubbed
  reliably. This is a policy point for the owner, not a bug.
- `flutter_secure_storage` on Flutter web keeps values in browser storage. Only relevant if the web build is
  ever used by patients (the owner mentioned testing over the LAN).
